## 本轮发现

### P02-R01 [P1] 删除会话可删除刚启动的运行

位置：`backend/app/services/runs.py:473–490`，特别是 `483–488`。

删除在事务外读取 `active_run_id`；随后事务无条件删除该会话的全部消息、事件和运行。若检查后另一个请求创建了新运行，删除事务仍可成功；事务重试也不复查活跃状态。违反 P02-A06“运行中删除返回 409”，可造成运行记录丢失、执行器写回失败和观察接口 404。

主审使用真实 Mongo replica set、独立 `technologyagent_test_review_p02_*` 库验证：先完成一条运行；暂停 DELETE 的首次读取返回；同 thread 创建新运行；放行 DELETE。实际输出 `deleted=true, new_active_run_missing=true`，退出码 0。探针只控制读取返回时机，创建、事务、删除均使用实际服务与仓储；finally 已删除该隔离库，没有写开发库。

修复要求：每次事务重试都读取并检查当前 thread；通过带空闲条件的 thread 写入/删除参与与认领操作的事务竞争，只有成功取得删除资格才删除关联记录。仅把普通读移进事务、没有条件写入，不足以表达互斥要求。

### P02-R02 [P2] 旧会话响应覆盖当前选择

位置：`frontend/src/hooks/useChat.ts:69–98`，关联 `108–163`、发送流回调和新对话操作。

`loadThread` 多次等待后直接 `adopt(next)`，没有操作代次；`recoverRun`、`refreshAfterRun` 及旧 SSE 回调同样可修改共享状态。React/JSDOM 执行实际 hook、替换 API/流依赖的内存探针复现：A 加载未返回→B 加载完成→A 晚返回，当前 thread 从 B 回到 A；A 加载中→新对话→A 晚返回，null 又回到 A。会话内容和 URL 会回退，下一条消息可能发进错误会话。现有切换 E2E 在两个运行均完成后顺序切换，未覆盖这些条件。

主审补充真实 Chrome 复现：拦截 A 的 conversation 请求并挂起，点击 B 等 URL 已指向 B，再放行 A，URL 实际回到 A；探针输出 `overwritten=true`。使用本轮隔离浏览器库，未修改产品代码。

修复要求：统一页面/会话操作代次；选择、新对话、刷新与卸载使旧操作失效；所有异步成功、错误、finally、恢复与流回调在写状态前核对所属代次和 thread/run。不能只给 `loadThread` 加一处判断。

### P02-R03 [P2] 会话预检查等待期间可重复发送

位置：`frontend/src/hooks/useChat.ts:177–191`。

`send` 等待 `ensureLocalSession()` 后才认领 `sendingRef`。实际 hook 内存探针中，延迟会话检查并连续调用两次 send，等待期间 `busy/sending=false`；放行后产生两个 `startSSE`，都是新 thread、不同 request_id。它们不是同请求重放，后端幂等键不能消除此重复；后一个观察流还会中断前一个。

主审补充真实 Chrome 复现：挂起 `/api/session/me`，发送第一条、再次输入第二条并发送，再放行会话检查，实际捕获 2 个 POST 流请求及 2 个不同 request_id。第一条提交后输入框清空会使空文本发送按钮暂时禁用，重新输入即可再次发送；这与发送互斥是否生效应区分。浏览器探针只证明两次流请求，不把请求数直接记为两条持久化 run。

修复要求：第一次 await 前同步认领发送状态；会话失败释放，连续提交只执行一次；检查返回时核对页面代次，避免用户切换/新建会话后旧预检查继续创建运行。

### P02-R04 [P2] 注册执行预算前的取消通知丢失

位置：`backend/app/services/chat.py:120–132`，关联 `53–56`、`200–203`。

运行已持久化而 `run_started` 尚未写完时，其他请求可从历史获得 active_run_id 并取消。DB 的 `cancel_requested` 成功写入，但任务表中没有 budget，通知没有落点；随后创建的 budget 不读取持久化取消标志。实际服务的内存调度探针中，取消后执行器仍产出全部后续 token 并返回 completed；`finish` 仅把最终显示改为 cancelled。这不满足 P02-A05 的“不再调度后续步骤”。该探针替换了持久层依赖，不冒充真实 DB 并发验收。

修复要求：先建立可接收通知的预算，再在开始执行前同步可信持久状态，保证窗口前后任一次取消均可见；不能仅修饰最终状态。保留正常重复取消和已完成运行的幂等行为。

### P02-R05 [P2] 已有会话相同 request_id 并发返回 409

位置：`backend/app/services/runs.py:150–159`、`181–202`、`234–244`。

两个相同请求都在事务前查不到已有 request；第一个提交，第二个在读取或 WriteConflict 重试时先遇到 active_run_id，返回 ACTIVE_RUN_EXISTS，而没有返回同一运行。现有相同请求并发测试覆盖新 thread，未覆盖已有空闲 thread。

主审在真实隔离 Mongo 中，让两个首次幂等查询都先返回空，再同时继续实际事务。结果是一条新 run 和一次 `ACTIVE_RUN_EXISTS/409`；已清理隔离库。P02-A04 应当返回同一 run；不同 request_id 的活跃竞争仍应 409。

修复要求：每次事务及竞争重试在判断活跃冲突前重新检查 owner/request_id 和 payload hash；相同 payload 返回原 run，变更 payload 为 IDEMPOTENCY_CONFLICT。保持只启动一次执行器、只写一条用户消息。

### P02-R06 [P2] SSE 终态检查可能漏发末事件

位置：`backend/app/api/chat.py:45–48`。

events(after_seq) 返回空后，finish 可能恰好提交；随后 get(run) 读到终态，路由直接退出，没有把已持久化的 run_finished/stream_end 发出。内存探针执行实际路由并控制依赖返回顺序，得到 `frames=[]`。客户端能走断流恢复，但正常连接不应因自身竞态漏末事件。

修复要求：观察到终态后，排空至该终态的 last_seq，确认已发送持久化 stream_end 才正常结束；增加确定性调度测试，避免靠 sleep 概率碰撞。测试也要确保异常情况下不会无限轮询。
