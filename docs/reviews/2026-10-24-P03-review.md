## 本轮发现

### P03-R01 [P1] 真实流式工具参数没有合并

定位：`backend/app/integrations/model.py:151–158`、`backend/app/agent/graph.py:120–129`。

适配器丢弃供应商 tool_call 的 index；图对每次 delta 用 `calls.setdefault(len(calls))` 新建调用，后续无 name 的参数片段又被过滤。主审执行实际 GraphExecutor，合法 inventory_get 参数拆为 `{"inventory_id":` 和 `"I001"}` 后，实际工具执行为 0，tool_finished 为 INVALID_ARGUMENTS。脚本模型一次传完整参数掩盖了此问题。

修复：稳定保留调用 index/id，按调用拼接参数，流完成后才解析执行；覆盖单调用分片、多调用交错、空首片、非法最终 JSON。不能仅在适配器单测断言“收到两个 delta”。

### P03-R02 [P1] 数量和金额没有与事实核对

定位：`backend/app/agent/evidence.py:22–30,39–48,69–75`。

证据只保存记录引用，不保存数量/金额；校验只要求匹配特定文字的回答有任意非空 evidence。主审实际图探针让工具返回 P001/W01 `shortage=55`，模型回答“缺口999；金额999999分。”仍为 completed。子审还确认“缺口是999”可绕过无依据检查。任何无关记录引用都不能证明对应数值正确。

这缺失 P03-T05 已要求的结构化数量/金额硬校验，不是要求提前完成 P05 的所有自然语言语义评审。应保留带实体/范围/字段/单位的事实，受控生成数值摘要或验证显式结构化结论；引用与数值绑定。避免继续堆正则来假装覆盖所有表达。

### P03-R03 [P1] live 验收可把假运行与失败结果判成通过

定位：`tests/live/test_readonly_agent.py:26–34,63–79`；关联 `scripts/verify_stage.py:210–213`。

测试只检查 run_finished 存在、工具名称和宽松字符串，没有核对 model_mode、终态、工具成功、参数、record_id 或 DB 事实。主审在无网络/无文件写入的受控探针中，执行实际测试函数，给它 9 份 `model_mode=fake / tool_finished=error / run_finished=failed` 的 SSE，只让 summary 含检查字符串，实际仍 accepted 9/9。这是验收器反例，**不是 9 次真实模型通过**。

此外 P03 live manifest 固定为空，配置 Key 后统一入口仍永远 not_run；trace 只存答案、工具名和事件类型，也无法做要求的事实对照。当前没有运行真实模型是正常限制；验收器可假通过和入口永久为空是需修复的实现缺口。

修复：验证服务实际运行模式与成功终态、成功工具调用及具体事实；记录脱敏 call_id/参数/结果/记录引用/模式/模型名/时间与对照。统一 live 入口接真实检查，缺配置 exit 2 not_run，有配置才显式执行，不能把 pytest 全 skip 的 exit 0 当 live 通过。

### P03-R04 [P2] 禁止的结论先推送再检查

定位：`backend/app/agent/graph.py:112–119`、`368–375`；持久化入口 `services/chat.py:28–29`。

token 在最终校验前直接写 sink。主审探针中“已下单，订单已创建。”最终 failed/UNSUPPORTED_OPERATION，但相同正文已发送到 sink；生产 sink 会先持久化并推送浏览器。失败状态不能撤回已展示的错误业务结论。

修复：业务结论通过校验后才作为正式回答发布；可先展示已有工具进度。明确未经检查的模型中间文本与正式回答的关系，保证历史也不会把被拒绝文本保留为成功结论。保留 P02 消息/事件去重契约。

### P03-R05 [P2] 最后一轮可以越过总时限并成功

定位：`backend/app/agent/graph.py:112–119,134–137,361–377`；预算只在 charge_model/charge_tool 前检查活跃时间。

主审注入 monotonic，预算从 0 开始，模型产生 token 前推进至 181 秒，max_active_seconds=180，实际仍 completed。179 秒开始的最后一次模型调用仍可使用整个 60 秒请求超时，结束后没有成功前检查。

修复：把剩余总时限纳入模型、工具和必要准备过程的 timeout；调用后与最终成功前检查活跃预算。继续保留失败调用扣计数、取消和 DB 原子上限，不实等 180 秒测试。

### P03-R06 [P2] P02-R02 仍有同视图连续运行窗口

定位：`frontend/src/hooks/useChat.ts:152–165`、`217–228`。

切换/new/refresh/unmount 的 view generation 已修复；但同一视图续发两轮共用 generation，旧 refreshAfterRun 只验视图、不验所属 run。实际 React/JSDOM hook 内存探针：old 终态触发刷新并挂起→续发 new 且收到 run_started→放行 old 刷新→发送 new token，状态从 `new/running/sending=true` 退回 `old/completed/messages=[]/sending=true`，新 token 被 reducer 的 runId 检查丢弃。

修复：新发送使旧运行异步操作失效，或引入单独 run/操作代次并在恢复/结束刷新写回前校验。view 与 run 两层保护均须保留；补正常连续续发的受控延迟测试。

### P03-R07 [P2] 模型提前 EOF 被当成完整成功

定位：`backend/app/integrations/model.py:130–168`。

适配器只判断是否收到过 data，没有验证合法结束。主审通过 httpx.MockTransport 返回 HTTP 200、一个 content 增量后正常 EOF，没有 DONE 或 finish_reason，真实适配器→GraphExecutor 返回 `completed / partial response / error=None`，把截断回答保存成成功。

修复：跟踪所支持供应商协议的结束条件；提前 EOF 报 MODEL_PROTOCOL_ERROR，终止当前回答，不把部分参数或正文当成功。覆盖合法完成、工具结束、无 usage、显式错误、连接中断；不用真实付费调用验证协议边界。

### P03-R08 [P2] 历史回答被统一标成最新模型模式

定位：`frontend/src/components/chat/MessageList.tsx:16–19`；关联 useChat 仅加载 latest run 事件与 ChatMessage 缺少模式维度。

实际 reducer/mergeHistory/MessageList 的内存 React 渲染证明：最新 fake 时历史 live 回答的 header 为 ScriptedModel；最新 live 时历史 fake 回答的 header 为 Live Model。同一仓库切换模式后继续会话即可形成这种历史。

修复：每条 assistant 根据自身 runId 的持久化模式元数据标注。当前运行徽标可展示当前模式；历史未知信息不能推断为 live。不要只改全局标题文字。

### P03-R09 [P2] MCP 发现失败后连接未清理

定位：`backend/app/integrations/mcp.py:133–137`；关联 `backend/app/agent/graph.py:309`。

工厂打开客户端后 list_tools 失败，没有关闭；GraphExecutor 在 try/finally 之前创建 registry，也无法清理未返回的对象。子审执行实际工厂、替换客户端与签发依赖的内存探针，得到 opened=1、closed=0。重复发现失败会遗留连接/后台任务。

修复：工厂负责失败/取消时关闭部分建立的客户端；成功返回后由 executor 负责正常关闭。覆盖连接成功后发现失败、取消和正常退出，避免 cleanup 异常覆盖原始错误。
