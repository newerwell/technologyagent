## P04 发现

### P04-R01 [P1] 失去租约的旧执行者仍可提交

定位：`backend/app/services/mutations.py:141–144,204–207`；`backend/app/repositories/operations.py:69–75`。

事务只检查 operation 是否 succeeded，没有验证本次 lease_owner 和有效期；mark_succeeded 按旧 lease_owner 更新，却不检查修改数量。主审真实 Mongo 隔离探针在旧执行者认领后推进时钟 121 秒、让新执行者重新认领，再继续旧事务，实际得到：`new_lease_claimed=true, execute_status=succeeded, orders=3, inbound=65, operation_status=processing`。真实 reconcile 返回 `409 INTERNAL_ERROR`，因为订单存在但操作记录不是成功。此处基线订单为 2，恰好新增 1 单，已经破坏订单/审批/操作结果的原子一致性。

修复：在事务中用当前租约进行有条件读写并建立竞争，校验仍归本次执行者；最终写结果必须匹配一条，否则抛错回滚整个事务。15 秒事务上限不能保护“取得租约后尚未进入事务”的长暂停窗口。

### P04-R02 [P1] 订单工作流未接入取消控制

定位：`backend/app/api/runs.py:46`、`repositories/runs.py:239–249`、`services/order_workflows.py:138–163`；关联 `services/runs.py:435` 的完成状态转换。

取消入口只通知 ChatTaskManager，订单图既不注册预算，也不检查持久取消。waiting_input 不在 set_cancel_requested 的匹配状态里，取消返回原样运行。主审真实 Mongo 探针：等待审批→cancel，仍 `waiting_input/cancel_requested=false`→继续 approve，最终 completed 且订单 2→3。运行中取消也不能阻止订单节点，收尾又可能仅把成功标成 cancelled，掩盖已经发生的写入。

修复：等待中取消应明确结束中断/审批与运行、释放 thread；执行中的取消在提交边界前阻止新副作用，提交后保留真实订单/对账结果，不以 cancelled 文本遮盖事实。保留普通聊天取消回归。

### P04-R03 [P1] resume 崩溃窗口忽略已有检查点

定位：`services/order_workflows.py:157–163`、`services/runs.py:668–700`。

resume 先清 pending 并置 running，再调用图；重启恢复只保留静止 waiting_input，其他一律按旧 P02 规则失败。主审使用真实 Mongo saver：已有 4 条检查点→执行 resume_waiting 后模拟服务关闭重开→检查点仍有 4 条，但 run 为 `failed/PROCESS_RESTARTED/pending=None`。已持久化的可恢复状态被运行入口锁死。图/订单已提交但 `_settle` 未完成的窗口也需按实际 operation 核对，不能统一写失败说明。

修复：持久化本次恢复决定/请求归属，依据真实 checkpoint 和 operation 恢复同 run；分别验证“认领后未入图”“提交后未写终态”。不能只再次覆盖静止 waiting_input 的重启测试。

### P04-R04 [P2] 重放与并发请求未始终收敛

定位：`services/mutations.py:88–107`、`services/order_workflows.py:139–144`、`frontend/src/hooks/useChat.ts:306–325`。

两个入口均有缺口。主审真实 Mongo 屏障探针让 B 首次查询 operation 返回空，A 随后完整提交；放行 B 后因审批 consumed 返回 `403 APPROVAL_REQUIRED`，没有返回同一成功结果。成功后重复同一 approve/resume 也得到 `409 RUN_NOT_ACTIVE`，没有核对原决定/operation。聊天 resume 等待期间未认领 busy/sending，卡片仍可继续提交；组件测试仅手工传 busy，没有验证真实父级流程。

修复：决定请求保存幂等键与 payload hash，重放优先返回原结果/处理中状态；相同键不同决定拒绝。遇到 consumed 的竞争先核对相同操作结果。前端在首个 await 前认领提交状态，但不能用按钮锁替代后端幂等。

### P04-R05 [P2] 多供应商仅处理第一张草稿

定位：`backend/app/agent/order_nodes.py:63–66,88,98–110,129–131`。

prepare 可以返回多张草稿，但审批只取 `[0]`，随后用 `[draft]` 覆盖列表，提交后直接 END。主审在独立库制造合法 P002/W01 缺货，P001/P002 分别推荐 S02/S01；新增两张草稿（含历史 seed 草稿的总数 2→4），批准首张后 run completed、pending=false，新增第二张仍 draft。不是所有采购内容都已完成，却没有继续确认或明确未完成项。

修复：持久保存剩余草稿和每张结果，逐张独立确认/拒绝/编辑，全部处理后才完成；恢复不能重复已提交草稿，多张卡片的编号不能只用 version 产生碰撞。

### P04-R06 [P2] 订单页和聊天工作流绕开彼此状态

定位：`frontend/src/app/orders/page.tsx:44–61,90–97`；关联 `agent/order_nodes.py:69`。

订单页可列出聊天中断的同一草稿，但直接 patch/resolve/create，不 resume 原 run。主审按真实页面调用顺序执行实际服务与 Mongo：订单页批准后订单数 3，原 run 仍 waiting_input；回聊天批准，图重放 approvals.request 遇到 approved 草稿而报错，运行变 failed、HTTP 500。编辑/拒绝也会使 checkpoint 版本或草稿状态失配，thread 持续占用。

修复：工作流所属草稿在所有页面通过同一个 resume/决定入口；独立草稿可保留独立操作，但归属必须由服务端返回。批准、拒绝、编辑、对账之后工作流与订单事实一致。

### P04-R07 [P2] 可纠正输入错误永久消耗中断

定位：`services/order_workflows.py:143–171`、`agent/order_nodes.py:79–86`。

edit 的完整字段校验发生在 resume_waiting 清 pending 之后；任何异常又统一把 run 标 failed。主审真实 Mongo 探针发送合法外层 ResumeRequest、`decision=edit,payload={}`，实际得到 `500 DEPENDENCY_UNAVAILABLE / run=failed / pending=None`，无法修正表单重试。非法仓库、数量、报价同属需区分的输入/业务错误。

修复：认领前进行决定与字段验证；可纠正 422/409 保留或重新建立有效等待。不要把所有业务异常转换成不可恢复的内部错误，也不能为恢复而绕过版本检查。

### P04-R08 [P2] 停用零件仍可批准采购

定位：`services/drafts.py:41–58,99–137`、`services/mutations.py:161–188`。

准备、修改和提交缺少 Part.active 检查。主审在真实隔离库把 P001.active 改 false，仍成功准备、人工批准并创建订单，订单数 2→3。有效报价/库存存在并不代表零件仍允许采购，违反 P04-T01 有效零件约束。

修复：准备与修改校验存在且 active，提交事务重查；准备后停用也应使旧批准失效。错误时不得新增订单或修改 inbound。

### P04-R09 [P2] 订单意图模型调用绕过幂等与预算

定位：`services/order_workflows.py:50–64,107–116`。

live 意图抽取发生在 create_or_get 前，直接 model.stream，没有 RunBudget 或持久模型计数。主审用实际服务/数据库、受控 ScriptedModel 执行该路径两次相同请求，得到 `same_run=true, model_calls_actual=2, model_calls_persisted=0`。这不是真实供应商调用；反例证明重放会重复模型请求，甚至可能在已有结果时因第二次模型失败而无法读回原结果。

修复：先认领并校验完整工作流请求/hash，重放返回原运行；模型只在受控 run 内执行，计入共享预算、取消和时限，并记录真实模型/意图证据。fake 模式的 draft 输入也应进入工作流幂等 payload 语义。
