## P05 发现

### P05-R01 [P1] 提交后的评审异常让运行卡在 reviewing

定位：`backend/app/services/order_workflows.py:177–190,362`，首次启动的结算调用亦在图执行保护之外。

订单事务成功后才执行 `_settle`；其中模型异常、取消、预算异常没有统一收尾，resume 的异常保护又已结束。主审真实 Mongo 隔离探针在批准后注入 `ModelProviderError`：基线两单变三单、成功 operation 增加一条，但 run 仍 `running`、phase=`reviewing`，没有 review/result 终态，已有 stream_end 只有 waiting_input。这不是订单未提交，界面和重试必须保留真实提交结果。另一个受控探针验证预算拒绝也绕过 finish。

修复条件：结算和恢复共用保护入口；模型错误/限额/取消均可靠终止或进入可恢复状态，保存已提交结果、错误码与未完成评审；重复恢复只读核查，不能重进提交节点。增加提交后 provider error、cancel、deadline、limit、重启各分支的数据库与事件断言。

### P05-R02 [P1] 订单语义失败没有修订，A04 未实际覆盖

定位：`backend/app/services/order_workflows.py:174–210`；`evidence/P05.md` 的 A04 映射。

订单路径仅调用一次语义评审，所有 revision_count 固定为 0；评审要求补充说明时立即 finish failed。主审真实 Mongo 探针：成功下单后模型返回 `passed=false`、要求补充已确认单号，实际仅一轮模型/评审，run failed，revision_count=0；订单仍已成功且仅新增一单。现有 live 轨迹是首轮即通过，不能证明“要求补说明后修订”的 A04。

同一路径在硬检查失败时仍调用语义模型；新建 RunBudget 还重置活跃时间（累计预算残留见前置表）。修复应执行最多两次只读补查/改写、三次检查；硬失败不进语义评审，不修改审批或订单。连续失败也必须说明已提交哪些订单，而不能笼统称“订单事实检查未通过”。

### P05-R03 [P1] 语义评审丢失原始请求

定位：`backend/app/agent/state.py:13–33`、`graph.py:378`、`review.py:212`；订单路径 `order_workflows.py:181`。

GraphExecutor 初始化 task_summary，但 TypedDict 未声明，LangGraph 状态过滤后评审读到空字符串。主审使用真实 GraphExecutor、LocalToolRegistry 和隔离 Mongo 运行 `P001 在 W01 缺多少？`，工具成功、run completed，捕获的语义输入 `request=""`。订单路径则把执行结果 summary 同时当 request 和 answer，仍无法判断是否遗漏用户要求。

修复条件：持久化不可变的原始请求/任务约束，并传入聊天、订单及重启恢复后的每轮评审；修订提示不能覆盖它。测试需捕获实际 ModelPort 输入，而非只对 semantic_review 手工提供完整 state。

### P05-R04 [P1] 正常只读任务被分配无法完成的计划

定位：`backend/app/agent/harness.py:77–105`。

主审真实 GraphExecutor + 本地只读工具探针：

| 用户问题 / 实际工具 | 结果 |
|---|---|
| 哪些零件要补货？只看W01。 / replenishment_preview | 工具成功、回答缺口55件，但“补货”被分成 order，要求 prepare/approval/order_result 三步；三轮 PLAN_COMPLETE 失败，三步全 pending |
| 查询W01库存预警 / inventory_warning | 工具成功、答案正确，但 inventory 计划未包含该既有工具；三轮 PLAN_COMPLETE 失败，步骤 pending |

计划必须匹配实际执行器能力与用户是否要求写入，不能只因出现采购/补货词要求人工批准；九种既有只读工具都应可完成对应查询。另见 graph 仅在成功分支注入 tool_name，工具失败时计划更新缺少动作名，界面可能持续 running；修复时一并验证失败→重试成功的计划状态。

### P05-R05 [P2] 成功空查询无法完成计划

定位：`backend/app/agent/harness.py:126–138`、`agent/evidence.py:94–102`、`contracts/workflow.py`。

done 要求有实体引用，但 `records=[]/total=0` 不产生实体引用。主审查询 W99 库存，inventory_page 成功返回空页，答案“该仓库没有库存记录。”仍三次 PLAN_COMPLETE，计划停在 running。零记录是有效查询结果，不应该靠伪造实体解决。

修复条件：增加受控的查询级依据（call_id、数据源、参数范围、观察时间、成功/total），与实体事实区分；空结果允许完成“查询”步骤，不能支持不存在实体的数值结论。同步 Python/事件/前端契约及旧快照兼容。

### P05-R06 [P1] live 门槛可接受 fake 和无关答案

定位：`tests/live/test_harness_review.py:24–98`。

skip 条件仅检查测试进程配置，断言只看阶段、某个 done、有 token、服务自报 review passed 和 completed；不检查服务实际 model_mode，也不核对 P001/W01 缺口。主审直接调用真实测试函数，替换 HTTP/Mongo 边界、阻止 trace 落盘：返回 `run_started.model_mode=fake`、错误实体引用、完全无关正文、伪通过 review，测试仍无异常。该反例证明门槛不足，不代表历史真实调用一定用了 fake。

修复条件：校验服务模式、真实工具轨迹/参数/来源、最终答案确实回答固定问题及字段值；复用加强后的独立答案验收器。fake、无工具、无关套话、错误实体/值、空事件、全 skip 必须失败。P05 live 不能替代 P03 固定三问各三次。
