## P08 问题

### R01 [P1] 数据源配置未贯穿页面/API与工作流，快照模式仍可本地下单

位置：`backend/app/bootstrap.py:123–149,172–173`、`api/catalog.py:53–60`、`api/drafts.py:117–120`。

`business_providers` 被创建后只供部分 MCP 分发使用；HTTP、草稿、原订单写服务及 fake 聊天仍依赖本地仓储。不是已配置远程失败后的显式报错，而是没有走选定 Provider。

真实 HTTP/Mongo 复现：将 suppliers/parts/inventory/orders 全部设为 `remote_erp`，不配置 ERP 端点；四类 HTTP 查询仍 200，目录/库存 meta 为 `local_seed`。按原草稿→批准→下单接口执行仍 200，订单 2→3，I001 inbound 10→65。再把四类设为 `local_snapshot`，得到同样写入结果，违反快照只读边界。

修复应将所有使用方接入同一 Provider/能力入口，跨模块组合提前验证；远程缺能力返回明确错误，快照写在副作用前拒绝，不能只在 MCP 包装层检查。

### R02 [P1] 改单批准未绑定价格快照，执行可按变化后的高价成交

位置：`services/approvals.py:40–49`、`services/business_mutations.py:166–179`；对照 `CONTRACTS.md` 的变价使审批失效约定。

真实隔离库复现：对 O001 批准 `order_update`，payload 为 `{"order_id":"O001","expected_version":1,"items":[{"part_id":"P001","quote_id":"Q01","quantity":10}]}`。批准后将 Q01 单价从 1200 改为 120000 分，再 execute；operation succeeded，订单金额从 12000 变成 1200000 分。提案中没有展示/绑定单价与总额，执行时直接读取实时 Quote 计价。

需要服务端生成可展示的变更草稿/规范提案，固定报价、金额与相关版本；执行重查发生变化时让旧批准失效，重新展示和确认。

### R03 [P2] 业务工具尚未接入聊天，通用批准后也没有可用的续接执行闭环

位置：`agent/graph.py:425–434`、`specialists/{analyst,order}.yaml:3`、`mcp_server/tools/specs.py:122`、`api/mutations.py:41–47`、`frontend/src/app/orders/page.tsx:28–36`。

实际 GraphExecutor/v2 + ScriptedModel，基础 registry 提供全部 `ALL_TOOL_SPECS`，调用 `mutation_prepare`、`order_statistics`、`part_by_supplier`，均得到 UNKNOWN_TOOL，基础 invoke 为 0；角色白名单仍只接 P03 九读工具和两项订单读工具。

页面真实 API 探针创建并批准 supplier_create 后，列表显示 approved，但 supplier_count=0，审批存储仍 pending。这本身符合“决定与副作用分开”的设计；缺口是页面没有执行入口、聊天没有该工具/持久等待与恢复路径，普通用户无法完成该业务动作。当前 E2E 只验创建/拒绝，不能证明批准后完成业务。

保持角色最小权限与人工批准，接通用户请求→提案→等待→批准→服务端执行→事实展示；不是给分析专家开放所有写工具。

### R04 [P2] 收货提案与执行采用不同规范化规则，合法乱序明细被误拒

位置：`services/approvals.py:40–41`、`services/inventory.py:37–55`。

真实隔离库先增加测试用P009/同单位“套”/S01有效报价与库存，通过正式HTTP草稿→批准→创建得到P001+P009的同供应商/仓库/单位双行订单。创建并批准 `items=[{P009:1},{P001:1}]` 的 inventory_receive，再按相同输入 receive，返回 APPROVAL_REQUIRED；按 P001/P009 排序重新准备并批准则成功。审批对原始数组哈希，执行先按 part 排序/合并再哈希；JSON schema 并未要求用户排序。P009仅为已清理隔离库中的测试夹具，未改种子目录。

使用一份 action-specific 规范化/校验函数同时生成展示、批准 hash 和执行 payload；乱序、重复行合并及非法行分别有确定性规则。

### R05 [P2] 通用提案的任意字典可绕过实体校验，写入导致目录读取 500 的坏数据

位置：`contracts/mutations.py:11–15`、`services/business_mutations.py:71–79`。

真实 HTTP 创建并批准 `supplier_create`，payload 为 `{"code":"BAD-SUP","name":123,"credit_rating":{"bad":"shape"}}`，随后正式 service execute 成功并记录 succeeded。再次 GET 该供应商返回 500，因为读取时 Supplier 模型拒绝 name/credit_rating。MCP 具体供应商工具的 schema 不能保护经通用提案保存的 payload；执行取的是保存内容。

按 action 定义服务端强类型 payload，提案准备与事务内执行都校验，拒绝非法类型/未知字段，坏提案不落业务数据、不消费批准。

### R06 [P2] ERP 分页缺字段且会把末页/重复记录误标全量

位置：`integrations/erp/mappings.py:35–44`、`mcp_server/tools/business.py:116–120`；消费处 `agent/graph.py:334–341`、`harness.py:196–214`。

生产纯函数复现：`records=[A,A],total=2,page=1,size=20`；`records=[C],total=21,page=2`；`records=[],total=21,page=3`，三者都返回 complete=true、无警告。仅收到末页不能证明前页已读，重复 ID 也不等于两条业务事实。

此外 `_map_remote` 即使单页全部返回，也缺共享分页契约的 `pages`，内部完整范围评审无法按契约验证；两处错误会分别造成外部错误声称完整与内部误拒。需要分清单页元数据和跨页收集完整性，保留可验证总量/页数及重复/矛盾告警，未知值不能伪造可信总量。

### R07 [P2] 远程订单统计被映射成单张订单，统计字段丢失

位置：`mcp_server/tools/business.py:110–121`；MCP capability 见 `mcp_server/server.py:95–97`。

`_map_remote("order_statistics", {"total":30,"total_cents":12345,"by_status":{"submitted":30},"scope_complete":true}, {})` 实际返回 id/number 为空、status=unknown、total_cents=None、items=[]，丢弃统计。原因是按 order_ 前缀统一选 map_order。需按工具结果类型分别映射，保留统计范围/金额/状态；与真 ERP 字段尚未实测是两件事。

### R08 [P2，交付契约缺口] 远程写仅有客户端预留，尚无持久批准/结果未知对账闭环

位置：`integrations/erp/client.py:22,48–74`、`erp_provider.py:22–31`、`mcp_server/tools/business.py:17–25`、`services/reconciliation.py:22–37`。

T05 勾选的持久 intent、owner/action/hash/version 批准绑定、远程结果回读核对、关联号恢复未接入服务。预留 MCP 分支仅检查非空 approval_id 就传 approved=True；未知关联号仅在客户端对象 set 中；现有 reconcile 只查本地订单。HTTP 模拟器复现：同一 client 对同关联号二次 write 被挡，但新建 client 后同关联号又发一次 POST，说明保护不能跨重启保留。read 的 remaining_budget 参数也未由 Provider 实际传入。

**目前两处装配都默认关闭远程写能力，本轮未证明实际远程绕过审批或重复建单。** 应补完整持久流程并在模拟器验证后再开放具体测试能力；或明确收回 T05 已实现的声明、将其保持开放缺口。缺少真实 ERP 环境不是本地持久实现缺失的原因。
